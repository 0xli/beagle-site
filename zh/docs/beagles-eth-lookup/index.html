通过 beagles.eth 名称查询 Carrier 地址

用普通的 ENS 库在以太坊主网上，从 Beagle 用户的 beagles.eth 名称读出其 Carrier 地址和 userid。不需要 Beagle API，也不需要密钥。

2026 年 11 月

能查到什么

Beagle 用户可以注册 help.beagles.eth 这样的名称。它的公开记录里有用户的 Carrier 地址，所以知道名称的人就能向对方发好友请求。任何支持 CCIP-Read 的 ENS 库都能读取：viem 2.35 或更高版本，或 ethers 6.17 或更高版本。

文本键含义
carrierAddressCarrier 地址：长格式，发好友请求时需要它
carrierUserIduserid：短格式，成为好友后发消息时使用
alias显示名称，例如 Beagle Chat Help
avatar图片地址。选用 CryptoPunk 时是 larvalabs.com 上的 PNG。用户没有设置时为空。

绑定的 Solana 钱包是地址记录，不是文本键：getEnsAddress({ name, coinType: 501n })。ENS 返回 32 字节公钥的十六进制形式，做 base58 编码后就是常见的 Solana 地址形式。

查询如何进行

ENS 并不保存这些值，下面的代码里也没有写任何 Beagle 服务器地址。每次查询的过程如下：

01
向 ENS 询问解析器

客户端向以太坊主网上的 ENS 注册表询问这个名称由哪个解析器负责。*.beagles.eth 的解析器是 Beagle 解析器 0x71B81d547de647D94a1892817c2Bc9BC93c5bAdd。

02
解析器发出重定向

解析器不保存资料数据。它返回一个 EIP-3668（CCIP-Read）重定向，指向 Beagle 网关。

03
网关为答复签名

客户端从网关取得记录，网关为答复签名。

04
解析器校验签名

客户端把签过名的答复交回解析器合约，由合约在链上校验签名。伪造或被改动的答复会被拒绝。

RPC 服务商和 Beagle 网关都能看到你查询的是哪个名称。

`getEnsResolver` 显示的是另一个地址

当前的 viem 和 ethers 通过 ENSv2 Universal Resolver 解析名称，所以 getEnsResolver 报告的是一个共用的 ENS 合约（查询 vitalik.eth 时也是它），而不是 Beagle 解析器。查询仍然会经过 Beagle 解析器和网关。

示例

mkdir ens-lookup && cd ens-lookup
npm init -y
npm i viem@^2.35

保存为 lookup.mjs：

// Read a Beagle user's Carrier fields through ENS on Ethereum mainnet.
// ENS does not store them: the resolver sends the lookup to the Beagle
// gateway and checks the gateway's signature.
import { createPublicClient, http } from 'viem'
import { mainnet } from 'viem/chains'
import { normalize } from 'viem/ens'

const name = normalize(process.argv[2] ?? 'help.beagles.eth')

const client = createPublicClient({
  chain: mainnet,
  transport: http('https://ethereum-rpc.publicnode.com'),
})

const [carrierAddress, carrierUserId, alias, avatar] = await Promise.all([
  client.getEnsText({ name, key: 'carrierAddress' }),
  client.getEnsText({ name, key: 'carrierUserId' }),
  client.getEnsText({ name, key: 'alias' }),
  client.getEnsAvatar({ name }),
])

console.log({ name, alias, avatar, carrierAddress, carrierUserId })
node lookup.mjs help.beagles.eth

输出如下：

{
  name: 'help.beagles.eth',
  alias: 'Beagle Chat Help',
  avatar: null,
  carrierAddress: '<Carrier address>',
  carrierUserId: '<userid>'
}

用 ethers 6.17 或更高版本（npm i ethers@^6.17），同样的查询是：

import { ethers } from 'ethers'

const provider = new ethers.JsonRpcProvider('https://ethereum-rpc.publicnode.com')
const resolver = await provider.getResolver('help.beagles.eth')

const carrierAddress = await resolver?.getText('carrierAddress')
const carrierUserId = await resolver?.getText('carrierUserId')

console.log({ carrierAddress, carrierUserId })
  • 缺失的值是 `null`。未注册的名称、已过期的记录、用户没有设置的键，都返回 null。使用 viem 时，给 getEnsText 传 strict: true，查询失败或答复被拒绝时就会抛出错误。
  • 名称是小写的。normalize 会把 Help.Beagles.eth 变成 help.beagles.eth，网关也接受任意大小写。
  • 任何以太坊主网 RPC 都可以。示例用的是一个公共 RPC；生产环境请用你自己的服务商。
  • 旧版本的库会失败。viem 2.35 之前的版本（例如 2.21）会调用一个已停用的 ENS 批量网关，查询会抛出错误。

发送好友请求

发好友请求用的就是 carrierAddress。使用 agent-mesh 时运行 mesh friend <carrierAddress> "hi"。在 Beagle 应用里，把它粘贴到添加好友的地方。

地址里包含 userid，所以可以核对这两个键是否一致。@decentnetwork/peer 提供了这个函数：

import { carrierIdFromAddress } from '@decentnetwork/peer'

if (carrierIdFromAddress(carrierAddress) !== carrierUserId) throw new Error('address and userid disagree')
名称不等于本人

beagles.eth 记录只说明记录所有者写了什么。关系重要时，先通过其他渠道确认名称，再接受好友。

其他 ENS 工具

  • ensdata.net 等 API 只返回一组固定的标准字段。它们从不查询 carrierAddress 或 carrierUserId，所以那里永远看不到这两个键。
  • ENS 没有“列出全部记录”的调用。客户端只能拿到它按名称查询的键，所以通用的 ENS 应用不会显示 Carrier 键。
  • 标准键（例如 description 和 url）按用户保存的原样返回。
